## 0. Стиль ответов

- Отвечай по-русски, максимально кратко и по делу.
- Без вступлений, пересказа задачи и итоговых резюме.
- Не объясняй очевидное; детали — только если спросят.
- После правок кода: 1–2 строки (что изменено, что проверено).
- Вопросы — только если без ответа нельзя продолжить.
- **Лимиты объёма [owner 2026-10-15]** — человек читает медленнее агента:
  - обычный ответ — до 400 знаков (~4 строки); анализ/разбор — до 800 знаков;
  - схема разбора: суть (1 строка) → причина (1–2 строки) → предложение;
  - список — до 5 пунктов, пункт — 1 строка (до ~100 знаков);
  - варианты решения — до 3, по строке, рекомендуемый первым;
  - без шагов воспроизведения, координат, логов и цитат кода — только вывод;
    подробности — по запросу владельца.

## 4. Железные правила

- **Тесты НИКОГДА не пишем и НИКОГДА не запускаем** [owner]. Старые тесты
  `*.test.ts.disabled` / `*.fixture.ts.disabled` не трогаем и не чиним.
- **Git:** работа в рабочей ветке отдельными коммитами, затем merge в `master` [owner 2026-10-14].
- Любое изменение графа — команда через `CommandBus` (immer `produceWithPatches`);
  UI не мутирует состояние напрямую.
- 4 слоя `domain → application → infrastructure → presentation` (enforced lint).
  Внешние контракты — только за портами `application/ports`.
- UI только из `@blueprint-vendor/*`; импорт `@material-ui/*` в `src` запрещён.
- Цвета только из темы `src/presentation/theme/editor-theme.ts`; hex в компонентах запрещён.
- Вёрстка — `div` + `makeStyles`; `Box` не использовать (пересчёт стилей на каждый рендер
  тормозит UI) [owner 2026-10-15]. Старые `Box` убирает план `docs/refactoring/R-BOX-layout.md`.
- Клавиши — только система хоткеев `features/hotkeys` (команда в `hotkey-commands.ts`,
  комбинация в `default-keybindings.json`, обработчик — `useHotkeyHandlers`); свои
  `onKeyDown`/`keydown` для хоткеев запрещены (поведение полей ввода — можно) [owner 2026-10-15].
- Принимающие (target) handles в покое невидимы и не ловят мышь; появляются только во время
  протягивания связи и только у допустимых целей (ADR-14). Постоянных target-точек не добавлять.
- Комментарии в коде — по-русски, со ссылкой (T-xxx, D-x, ADR-xx, Nx).
- Коммиты — conventional commits по-русски (commitlint проверит).
- Нельзя ослаблять tsconfig/eslint ради зелёного lint.
- **Стоп-условия** (остановиться, доложить владельцу): конфликт peer-зависимостей,
  пакет не найден, API пакета не совпадает со спекой, нужно менять конституцию.
  `--force` / `--legacy-peer-deps` — только с разрешения владельца.

## 4a. Проектирование [owner 2026-10-15]

- **Одно понятие — один механизм.** Перед правкой поведения сущностей (выделение,
  подсветка, dnd, уровни, порядок, связи) найди ВСЕ его реализации (`code-finder` / grep).
  Механизмов ≥2 — не латай симптом молча: в ответе назови параллельные механизмы и
  предложи объединение (1–3 строки); объединяет агент только по решению владельца.
- **Общее поведение — композиция, не копия и не наследование.** Сущности — данные
  (zod + union по `kind`), поведение — чистые функции/хуки, различия — параметры
  (scope, рёбра, ограничения). Эталон — `domain/layer-depths.ts`, `domain/connection-rules.ts`.
  «Сделать как у X» = вынести общее ядро из X, а не копировать X.
- **Визуальное состояние сущности — одно значение с явным приоритетом**
  (цель связи > цель dnd > выделение > ошибка) и одна геометрия рамки; новый вид
  подсветки — новое значение, а не новая рамка.
- В отчёте после правки поведения: «точечно / объединил; параллельные механизмы: …».
- **Обратимость решений [owner 2026-10-16].** Ограничение/правило заказчика — данные
  (таблица, поле политики), а не ветвления: смена или отмена = правка одного значения.
  Одно правило — один источник: его читают и инвариант домена, и подсказки UI
  (эталон — `domain/layer-capacity.ts`).
- **Открытость к расширению [owner 2026-10-16]** (Open/Closed + Strategy): новый вид
  сущности/связи/подсветки — запись в таблице или новая стратегия, ядро не правится.
  Аудит кандидатов на вынос в конфиг — `docs/refactoring/A-CFG-config-audit.md`.
- Карта «сущность × возможность» и известные дубли — `docs/refactoring/R-ENT-entities.md`;
  все отложенные рефакторинги и как их запускать — `docs/refactoring/README.md`.

## 5. Команды (вывод уже сжат — не запускай «сырые» варианты)

| Команда                                | Зачем                                                                        |
| -------------------------------------- | ---------------------------------------------------------------------------- |
| `npm run verify`                       | lint + build (сам — в pre-commit). Ошибка — только ошибки + путь к логу      |
| `npm run rules`                        | правила §4, не ловимые eslint (hex, `@material-ui`, `window`; в pre-commit)  |
| `npm run ui -- <шаги>`                 | ручная проверка UI текстом (сам поднимет dev-сервер); шаги — в шапке скрипта |
| `node scripts/agent/lint-file.mjs <f>` | eslint одного файла сразу после правки                                       |
| `npm run state:summary`                | что открыто в PROJECT_STATE и нужно ли его обновлять                         |
| `npm run state:section -- <id>`        | одна секция PROJECT_STATE с номерами строк (для правки)                      |
| `npm run state:check`                  | механическая сверка PROJECT_STATE с git/package.json                         |
| `npm run state:log -- <кто> "<что>"`   | бамп UPDATED + строка в CHANGELOG (вручную их не трогать)                    |

Полные логи — в `.agent-logs/*.log`; читай только нужный фрагмент (поиск по
файлу/строке), не целиком.

Стенд производительности — проект на главной («Стенд производительности»),
`/#/editor?project=stress` на dev-сервере; размеры графа — query
(`&levels=&pagesPerLevel=&elementsPerPage=&forms=&stepsPerForm=&fieldsPerStep=`).

## 6. Экономия контекста

- Не читай файл целиком, если нужна часть: сначала поиск, потом чтение диапазона.
- Не перечитывай файл, который только что прочитал или отредактировал.
- `git`: `status -sb`, `log --oneline -10`, `diff --stat`; полный diff — по одному файлу.
- Никогда не читай: `node_modules/`, `dist/`, `package-lock.json`, `*.disabled`, `docs/archive/`.
- Проверка UI — текстом (`npm run ui`). Скриншот — только если без картинки
  нельзя (вёрстка, цвет), и кадрируй по элементу: `--shot .agent-logs/x.png@<css>`.
- Код правь инструментом редактирования CLI, не shell-скриптами (python, `sed -i`,
  `>`): тогда сразу линтуется изменённый файл. В Claude Code shell-правки кода
  блокирует хук `bash-guard` [owner 2026-10-15].
- `verify` + `rules` вручную не запускай: их гоняет pre-commit (Husky) на каждом
  коммите с кодом [owner 2026-10-15]. В процессе хватает линта файла.
  Вывод команд не фильтруй повторным запуском — сразу `| tail`/`| grep`.

## 7. Чек-лист завершения задачи (выполни ВСЁ по порядку)

1. Если менялся UI — `npm run ui -- …` по сценарию задачи, `✅ ui OK`.
2. Коммит (conventional, по-русски). Pre-commit сам прогонит lint-staged, `verify`
   и `rules`; красное — коммит не пройдёт: исправь и закоммить снова.
3. Push рабочей ветки, merge в `master` и push `master`.
4. `npm run state:summary` — если «⚠️ ОБНОВЛЕНИЕ: вероятно нужно», напиши владельцу,
   что предлагаешь добавить в PROJECT_STATE (сам файл правит `/update-state`).
5. Ответ владельцу: 1–2 строки — что сделано и чем проверено.
