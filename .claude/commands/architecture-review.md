# Architecture Review (системный уровень)

Аудит структурного здоровья: границы, направление зависимостей, слои, дрейф от ADR.
Только отчёт — код не менять. SOLID/дизайн классов/стиль — вне scope.

**In scope:** границы модулей, циклы, нарушения слоёв, связность пространств имён, утечки публичного API, засорение общих моделей, дрейф от ADR.

## 1. Цель

- `pr <N>` / `branch <name>` → `git diff master...<branch>`, файлы через `git show <branch>:<file>` (в этой среде `gh` нет — только git).
- `namespace <path>` → рекурсивно файлы под `<path>`.
- пусто → весь проект: точки входа и верхнеуровневые модули `src/`.

## 2. Контекст проекта (не блокироваться, если чего-то нет)

1. `AGENTS.md` §4, §4a (правила, слои `domain → application → infrastructure → presentation`, порты, CommandBus).
2. `specs/000-constitution.md` (побеждает всё), `docs/декомпозиция-canvas-редактор.md` (T-xxx, D1–D13).
3. ADR — `npm run state:section -- 3` (PROJECT_STATE целиком не читать).
4. `eslint.config.*` (правила `eslint-plugin-boundaries`), `tsconfig.json` (алиасы).

## 3. Карта зависимостей

Импорты `import` сгруппировать по слоям и верхнеуровневым модулям; отметить:

- импорты через границу слоёв / «вверх» по слоям;
- импорт во внутренний подпуть чужого модуля (мимо публичного индекса);
- внешние контракты мимо `application/ports`;
- `@material-ui/*` в `src`, записи в `window` (ломают микрофронтенд, конституция §7).

## 4. Проверки (каждой находке — `file:line`)

1. **Направление зависимостей** — domain не знает о внешнем; adapters → ports → domain.
2. **Циклы** — граф уровня модулей; приемлемые циклы тоже в риски.
3. **Связность границ** — одна ответственность на модуль; «god module»; ширина публичного API.
4. **Засорение общих моделей** — сущности между контекстами без трансляции, разрастающие `common/util`.
5. **Дрейф от ADR** — для каждого ADR: код ещё соответствует? Указать ID и файл.
6. **Параллельные механизмы** (AGENTS.md §4a) — одно понятие реализовано ≥2 раз; предложить объединение.
7. **Генерируемость** (AGENTS.md §4b) — смысл экрана/элемента/перехода живёт вне `ServiceBlueprint`.
8. **Сквозные задачи** — мутации только через CommandBus; хоткеи только `features/hotkeys`.

## Правила

- Только чтение. Каждая находка — с `file:line`.
- Приоритизировать по серьёзности, не по количеству.
- Нет ADR/контекста — выводить намерение из структуры кода.
- Стиль — территория линтера/prettier, игнорировать.
- Только структурные находки; если остались лишь мелкие код-качества — так и сказать.
