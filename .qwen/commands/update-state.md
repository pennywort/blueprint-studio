# Команда: update-state

Ты обновляешь файл `PROJECT_STATE.md` в корне проекта. Этот файл — единственный источник правды о состоянии проекта для удалённых агентов без доступа к файлам. От тебя требуется ПЕДАНТИЧНОСТЬ, а не креативность.

Аргументы от пользователя (если есть): {{args}}
Если пользователь передал текст решения/факта — это источник `[owner]`.

## Шаг 1. Прочитай правила

Открой `PROJECT_STATE.md` и прочитай блок SCHEMA RULES в шапке. Соблюдай его буквально:

- структура секций и шапки таблиц НЕ меняются;
- статусы — только из enum'ов в комментариях секций;
- §9 CHANGELOG — append-only;
- после обновления бампни `UPDATED:` и добавь строку в CHANGELOG с пометкой `agent:qwen`.

## Шаг 2. Собери факты (ТОЛЬКО этими способами)

Разрешённые источники:

1. `git log --oneline -15` — что закоммичено
2. `git status --short` — незакоммиченные изменения
3. `cat package.json` — версии и наличие пакетов (секция §2 STACK обновляется ТОЛЬКО отсюда)
4. `ls` по каталогам `src/` — существование файлов (например, `ls src/application/commands/ src/infrastructure/`)
5. `grep` для проверки конкретных утверждений (например, `grep -rn "createContainer" src/` — используется ли awilix)
6. Сообщение пользователя в этом диалоге — помечается `[owner YYYY-MM-DD]`

ЗАПРЕЩЕНО:

- Выводить факты из имён файлов без проверки их содержимого, если факт касается реализации (файл может быть stub — проверяй содержимое, как в §5 инвариантов).
- «Вспоминать» состояние проекта из контекста диалога без верификации.
- Догадываться о причинах, намерениях, планах.
- Читать как источник фактов что-либо вне репозитория и вне разрешённых путей: запрещены `tmp_project_dir/`, `node_modules/`, отчёты и заметки (`*.md` кроме самого `PROJECT_STATE.md`). Разрешённые пути чтения содержимого: `src/`, `package.json`, корневые конфиги.
- Опираться на незакоммиченные изменения. `git status --short` читается только для информации; staged/unstaged-изменения — НЕ факты состояния и не основание править любые секции. Состоянием считается только закоммиченное.

## Шаг 3. Примени обновления

По каждому факту реши, куда он идёт:

- закоммиченная и работающая функциональность → §4.1 DONE
- отсутствующая/незакоммиченная → §4.2 NOT DONE
- решение архитектуры → §3 (новый ADR с номером = max+1; отменённое решение → status: superseded, строка не удаляется)
- изменение версий/пакетов → §2
- изменение статуса инварианта → §5 (проверь содержимое файла инварианта)
- непроверяемое/нерасхождение с реальностью → §6 с пометкой UNKNOWN
- изменение плана → §7 (выполненные пункты удаляются — факт переходит в §4.1)
- прогресс эпика → §8

Если файл/секция уже соответствует фактам — НЕ переписывай её.

## Шаг 4. Покажи diff и спроси подтверждение

Выведи `git diff PROJECT_STATE.md` (или unified diff), кратко перечисли, что изменил и почему (с указанием источника каждого факта). Спроси: «Применить?». Только после «да» — сохраняй.

Если обновлять нечего — так и скажи, ничего не меняй.
