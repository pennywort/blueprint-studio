# Дизайн: «Сложная логика» — условная видимость элементов

> Дата: 2026-10-08 · Основано на: макете «ГОСБ — список Московских банков» (связь option → Select), PROJECT_STATE.md, декомпозиция-canvas-редактор.md
> Назначение: проектное решение для реализующего агента. Реализация в этом документе не производится.

---

## 1. Суть фичи

На элементе-источнике (сейчас — только **Select**) включается режим **«Сложная логика»** (чип на карточке элемента, включается из инспектора). После включения у **каждого option** этого Select появляется source-handle, из которого пользователь протягивает связь к другому элементу формы. Смысл связи:

> «Когда в Select-источнике выбран этот option → целевой элемент становится видимым».

Пример с макета: option «Московский банк» (Значение 1) в Select «ТБ» → ребро к Select «ГОСБ — список Московских банков». В предпросмотре «ГОСБ…» скрыт, пока пользователь не выберет «Московский банк».

**Целевая аудитория — бизнес-пользователи.** Поэтому никакого редактора выражений, формул, операторов AND/OR и «программирования» — только протягивание связей, как это уже принято для связей элемент → подсценарий (см. декомпозицию T-032).

## 2. Принятые решения

| # | Вопрос | Решение |
|---|---|---|
| L1 | Что является условием | **Конкретный option конкретного Select'а.** Не «любое значение», не диапазоны, не сравнения. Условие = «в элементе X выбран option Y» |
| L2 | Что является действием | Только **`show`** (показать). Действие не выбирается — оно одно, выбор действия не предлагается. Обратный смысл («скрыть при…») достигается инверсией набора option'ов-источников |
| L3 | Поведение цели по умолчанию | Элемент, на который есть хотя бы одно правило, **скрыт по умолчанию** в предпросмотре/рантайме. Появляется, когда выполнено **хотя бы одно** правило (неявное ИЛИ между правилами). Несколько рёбер на одну цель — законно |
| L4 | Где включается | Свитч/чип **«Сложная логика»** в инспекторе элемента-источника. Включение не создаёт правил — только открывает возможность протягивать рёбра из option'ов. Выключение при наличии правил — с подтверждением и каскадным удалением рёбер |
| L5 | Источники на старте | Только Select (включая Selection list по макету). Модель проектируется расширяемой: Checkbox, Radio и др. добавляются новым **типом условия** без смены парадигмы UI (см. §4) |
| L6 | Цели | Любой элемент формы (Select, Checkbox, Text field, …) и, перспективно, целый шаг формы. Цель не ограничена типом — скрыть можно что угодно |
| L7 | Хранение | Правила — **отдельная коллекция `logicRules` в ServiceGraph**, а не внутри props элементов. Ребро = правило; удаление правила = удаление ребра. Это же упрощает инварианты и сериализацию |
| L8 | Чего НЕ будет (осознанный отказ) | Редактор выражений; AND/OR-группы; действия `hide/disable/setValue/required`; условия «не выбрано», «пусто», сравнения чисел/дат; правила между разными формами. Всё это — потенциальные расширения, но не первая версия |

## 3. Доменная модель

### 3.1 Типы (domain-слой, Zod)

```text
LogicRule = {
  id: LogicRuleId            // branded, как остальные ID
  sourceElementId: ElementId // элемент-источник (у него включена «Сложная логика»)
  condition: LogicCondition  // discriminated union — точка расширения
  targetElementId: ElementId // элемент-цель (скрыт по умолчанию)
}

LogicCondition =
  | { kind: 'optionSelected', optionId: OptionId }   // v1: Select / Selection list
  // будущее, без изменения обвязки:
  // | { kind: 'checkboxChecked' }                     // Checkbox: состояние «включён»
  // | { kind: 'radioOptionSelected', optionId }       // Radio
  // | { kind: 'toggleOn' }                            // Switch
```

Ключевая идея расширяемости: **вся механика (ребро → правило → видимость цели) опирается только на `LogicCondition` как union.** Добавление Checkbox позже = новый член union + новый визуальный источник handle'а (вся карточка чекбокса вместо строк option'ов) + новая строка в маппере оценки условий. UI парадигмы, инварианты, команды и сериализация не меняются.

### 3.2 Флаг на источнике

`hasComplexLogic: boolean` — в проектной схеме элемента-источника (meta-слой по D4 из декомпозиции, НЕ в element-schemas lib-app-core). Служит двум целям: (1) показ чипа «Сложная логика» на карточке; (2) рендер handle'ов у option'ов.

### 3.3 Хранение в графе

```text
ServiceGraph {
  ...существующее,
  logicRules: LogicRule[]    // новая коллекция, сериализуется вместе с графом
}
```

Рёбра на canvas — проекция этой коллекции через `graphToFlow` (см. §6).

## 4. Расширяемость без перегруза

Граница «расширяемо, но просто» держится на трёх уровнях:

1. **Условие — закрытый набор типов.** Бизнес-пользователь не конструирует условие, он выбирает «откуда тянуть стрелку». Состав типов условий контролируем мы (домен), а не пользователь.
2. **Действие — одно (`show`), семантика — одна (ИЛИ между правилами, цель скрыта по умолчанию).** Это покрывает заявленный кейс заказчика и типовые формовые сценарии («показать детали при выборе значения»), не превращая редактор в IDE.
3. **Новые источники подключаются декларативно.** Для каждого нового типа условия описывается: где рисовать source-handle (строка option'а / вся карточка), как оценить условие по состоянию формы, чип/подпись. Никакой новой механики рёбер.

## 5. Инварианты (чистые функции `(graph) => InvariantViolation[]`, как в PROJECT_STATE §5)

| # | Правило | Сообщение (пример) |
|---|---|---|
| L-I1 | Источник правила — элемент с включённой «Сложной логикой» | «Правило ссылается на элемент без включённой сложной логики» |
| L-I2 | `condition.optionId` существует среди option'ов источника | «Правило ссылается на удалённое значение списка» |
| L-I3 | Источник и цель существуют в графе; цель ≠ источник | «Правило ссылается на удалённый элемент» |
| L-I4 | Нет дублей: пара (sourceElementId, condition, targetElementId) уникальна | «Дубликат правила видимости» |
| L-I5 | Источник и цель — в пределах одной формы | «Сложная логика возможна только внутри одной формы» |
| L-I6 | Нет циклов видимости: цель правила не может (транзитивно) быть источником правила для самого источника в той же цепочке видимости* | «Циклическая зависимость видимости элементов» |
| L-I7 | Элемент-цель с `required` при скрытом состоянии не блокирует отправку — фиксируется как правило рантайма, а не инвариант графа (см. §7) | — |

\* Цепочки «A показывает B, B показывает C» — легальны (каскадные зависимости); запрещены только циклы.

## 6. UI/UX на canvas

**Карточка-источник (Select).** В инспекторе — свитч «Сложная логика». При включении: чип «Сложная логика» на карточке становится активным (залитый, как на макете у «ГОСБ…»); у каждой строки option («Московский банк», «Банк 2»…) справа появляется source-handle (как у связей элемент → подсценарий, T-032). Состояние чипа без правил и с правилами одинаковое; количество правил можно показывать счётчиком на чипе (опционально).

**Карточка-цель.** Входящее ребро крепится к левому краю карточки (target-handle на уровне карточки элемента, не шага и не формы). При наведении на карточку-цель во время drag — та же подсветка, что у подсценариев. Цель отображает индикатор зависимости (например, маленькая иконка-глаз у чипов), чтобы было видно «этот элемент кому-то подчинён» даже при выключенной логике у источника.

**Ребро.** Отличимый стиль от навигационных связей элемент → подсценарий: пунктир или другой цвет из темы (D6, цвета — только из объекта темы). Смысл рёбер разный (навигация vs видимость) — визуально путать их нельзя.

**Удаление.** Удаление ребра = удаление правила (команда). Удаление option'а, элемента-источника, элемента-цели или выключение «Сложной логики» → каскадное удаление зависимых правил (с подтверждением, если правила есть). Ошибки L-I1/L-I2/L-I3 тем самым в UI недостижимы, но инварианты остаются защитой данных.

**Инспектор цели.** При выборе элемента-цели — секция «Видимость»: текстовое резюме «Показывается, если в ‹ТБ› выбрано ‹Московский банк›» + список всех правил на эту цель с кнопкой удаления. Это единственное место, где логика видна списком — полезно, когда рёбра визуально далеко друг от друга.

## 7. Предпросмотр и рантайм-семантика

1. Цель с правилами **скрыта по умолчанию**; показывается при выполнении хотя бы одного правила (ИЛИ).
2. Скрытый required-элемент **не валидируется** и не блокирует переход по шагам/отправку; при скрытии его введённое значение **сохраняется** (не стирается) — пользователь мог временно переключить option.
3. Оценка условий — чистая функция `evaluateVisibility(rules, formState) => Set<ElementId>` в domain-слое (без React/Effector), используется и предпросмотром, и инспектором (подсветка «сейчас скрыт/виден» в режиме предпросмотра), и будущим генератором MicroAppDescriptor.
4. Каскад: если видимость B зависит от A, а C — от B, то скрытие A скрывает и C (C не может быть виден при скрытом B).

## 9. Открытые вопросы (к владельцу)

- ❓ **L-Q1.** На макете чип «Сложная логика» есть и у источника («ТБ»), и у цели («ГОСБ…»). У цели это индикатор «есть входящие правила» или признак того, что и она может быть источником? Принято: у цели — индикатор зависимости (иконка-глаз), чип «Сложная логика» — только у источников.
- ❓ **L-Q2.** Множественный выбор («Множ. выбор»): условие «option выбран» срабатывает, если он входит в выбранное множество? Принято: да, `optionSelected` = «входит в текущее значение».
- ❓ **L-Q3.** Значение скрытого элемента сохраняется (§7.2) или очищается при скрытии? Влияет на данные заявки.
- ❓ **L-Q4.** Нужен ли в v1 сценарий «шаг формы как цель» (скрыть целый шаг), или только элементы?
- ❓ **L-Q5.** Как правила сериализуются в MicroAppDescriptor для lib-app-core: есть ли у движка нативная условная видимость, или генерируем обработчик на нашей стороне? Блокирует T-068 в части экспорта (Epic 005), не блокирует редактор.
