# План: точные и стабильные схемы элементов

Основа: `docs/generate-element-spec.md` + примеры `docs/schemas/examples` (коммит 5e08130e).

## Главная идея

Формат схемы фиксируем **отдельно от скрипта**. Скрипт можно переписывать сколько угодно,
но выход обязан пройти проверку формата, а любое изменение схем видно отдельным diff-отчётом.

## Этап 0. Зафиксировать формат (до правок скрипта)

1. **Мета-схема формата** `element-schema.meta.json`: разрешённые ключи верхнего уровня,
   разрешённое подмножество JSON Schema у свойств (`type/enum/const/oneOf/anyOf/items/
properties/$ref/default/description`), обязательные `x-*`. Всё прочее — ошибка.
2. **Версия формата** `x-format-version` в каждой схеме. Ломающее изменение = +1 и запись в changelog.
3. **Единые имена расширений**: сейчас `elementType`, `deprecatedAliases` без `x-`.
   Переименовать сейчас, пока схемы ещё никто не потребляет.
4. **Маркер «не распознано»** вместо пустой `{}`: `{"x-unresolved": "<текст TS-типа>"}`.
   Тогда потребитель отличает «любое значение» от «скрипт не понял».
5. **Эталоны** (golden): `button` и `list-item`, выверенные вручную «как должно быть».

## Этап 1. Каркас скрипта (стабильность)

1. Разделить скрипт на **извлечение → IR (типизированная промежуточная модель) → вывод JSON**.
   Доработки точности трогают только извлечение; формат задаёт только вывод.
2. Перед записью — валидация мета-схемой + компиляция ajv (draft-07). Невалидно — не пишем.
3. Режим `--all`: все элементы за один прогон (программа типов грузится один раз) +
   **отчёт покрытия**: сколько `x-unresolved`, дефолтов-«кусков кода», пустых props-файлов.
4. `--check` на всех элементах в CI фреймворка; `--check` ничего не пишет (сейчас пишет иконки).
5. Детерминизм: порядок свойств = база, затем объявление; сортировка `required`, `enum` как в исходнике.

## Этап 2. Точность (по убыванию пользы, видно на примерах)

1. **Дискриминатор `type` во вложенных объектах выкидывается** → у `list-item.leftAtom/rightAtom`
   ветки `oneOf` одинаковые, схема невыполнима. Подтверждено: `createAtom`/`atomCreator` выбирают
   атом по `atom.type`. Сохранять `type` как `const`; отсев `type` — только на верхнем уровне элемента.
2. **Дефолт элемента перетирается базой**: у `button` `width` по коду `wrap_content`, в схеме `match_parent`.
3. **Унаследованные props** (`extends`) теряются. Брать все свойства типа с пометкой `x-origin`.
4. **`default: null` при типе без `null`** (`button.badge`) — схема противоречит сама себе.
5. **Обработчики** (`onClick`, `onChange`) → явный признак `x-kind: handler`, не `{}`.
6. **События** у всех одинаковые из ручного файла, там же невалидный `"type": "any"`.
   Источник без правок фреймворка: тип 2-го параметра `publishEvent` (у list-item — union
   `ItemEventClick` из `ListItemEvents`); из каждого типа брать `name`, `target`, поля payload.
7. **Методы**: имя параметра лежит в `description` → отдельное поле `name`.
8. **Описания** свойств из JSDoc; контейнерность — по иерархии типов, не по тексту `extends`.

## Этап 3. Потребление в blueprint-studio

1. Схемы приходят пакетом/копией с `x-format-version`; парсер — zod по той же мета-схеме.
2. **Политика редактора** — данные (таблица), не код: список элементов, видимые атрибуты,
   обязательность, порядок, подписи. Политика может только **сужать**: тип значения не меняется
   (проверка при загрузке: enum политики ⊆ enum схемы, иначе ошибка).
3. Сборка: схема фреймворка + политика → описание элемента, из которого UI строит форму атрибутов.

## Этап 3 — как устроено (2026-10-19)

- Решения владельца: элемент карты = `kind` (имя во фреймворке) + `props` по JSON-схеме, zod — только
  структура карты; компоненты (CI picker, поиск сотрудника, адрес, логин) и комментарий — схемы проекта;
  datePeriod → `date-range-field-picker`, infoBlock → `alert` (message-strip устарел во фреймворке [owner 2026-10-20]), Select list → `select` /
  `radio-group` (displayType radio).
- Схемы фреймворка: `npm run schemas:import -- [бандл | папка пакета]` → копия
  `src/infrastructure/element-schemas/framework/schemas-bundle.json` (без отчёта). Переход на npm-пакет
  меняет только источник JSON в `container.ts`.
- Схемы проекта: `src/infrastructure/element-schemas/project/project-schemas.json` (тот же формат).
- Политика редактора: `src/infrastructure/element-schemas/editor-policy.json` — элементы, атрибуты,
  обязательность, порядок, подписи, секции, варианты enum, `item` массивов объектов, `card`, `defaults`.
  Только сужает: тип значения — из схемы, enum ⊆ схемы. Проверка — `npm run schemas:check`
  (та же сборка `assemble-element-schemas.ts`, что у редактора при старте).
- Панель атрибутов показывает **только** атрибуты схемы + политики, ничего сверх [owner 2026-10-19]:
  свитч «Сложная логика» — на карточке элемента, правила логики удаляются ребром на канвасе;
  поле `comment` элемента (US-05) в панели не редактируется — для заметок есть элемент «Комментарий».
- Варианты источников логики (`select.options`, `radio-group.items`) — таблица `domain/element-kinds.ts`.
- Сохранённые карты: миграция записи v4 → v5 (`graph-record-migration.ts`); поля без пары во
  фреймворке теряются (maxLength, withTime, иконка List item, position кнопки, search списка).

## Этап 4. Схемы компонентов (2026-10-20)

Решения владельца: компонент — не элемент, а составная сущность из элементов с логикой
(`ComponentFactoryImpl<P, C, S>(ElementsTypes.X, { defaultProps, view, methods, slots })`); имя — член
того же `ElementsTypes`; компоненты лежат только в `packages/lib`, но имена файлов (и `types.ts`) не
гарантированы — опираться на пути нельзя.
