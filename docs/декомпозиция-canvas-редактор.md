## 1. Принятые решения (зафиксированы в этой сессии)

| # | Вопрос | Решение |
| --- | --- | --- |
| D1 | Редактирование Формы заявки | Узел на общем канвасе. Вложенность: Form → Step → Component. Шаги — **горизонтальные колонки** внутри узла формы (макет «добавление-шагов-формы-и-элементов-в-шаги»): у каждого шага свои корзина и «+» (добавить элемент в шаг). Чип типа формы в заголовке: «Одностраничная» / «Степперная» |
| D2 | Позиции узлов | Координаты **не хранятся** (на бэке их нет, там авто-выравнивание). Раскладка — слоистая, вычисляется из графа (см. D7). Хранится только **порядковый номер каждой сущности-страницы** (`orderIndex` 0, 1, 2, 3…, D13) — на сервере, как часть данных карты |
| D3 | Источник element-schemas | Архитектура через порт `IElementSchemaProvider` (уже есть). Сейчас — `ManifestSchemaProvider` + локальный `element-manifest.json`; при появлении доступа к пакету lib-app-core добавляется второй адаптер, presentation не меняется |
| D4 | Метаинформация атрибутов | Отдельного слоя не будет. label, helperText, required, placeholder, секции, условная видимость (кейс FAQ: «Вложение*» при включённой «Загрузке файлом») описываются **собственными схемами проекта**, расширяющими element-schemas. Панель атрибутов читает тип атрибута из element-schemas, мету — из проектной схемы; точно известно, что для чего используется |
| D5 | Поиск в шапке | Поиск по узлам и элементам канваса с подсветкой и центрированием вьюпорта |
| D6 | Темизация | Тема проектируется как система по механике MUI v4 (Flamingo): объект темы (palette + overrides) + `ThemeProvider`. По умолчанию одна тема — как на макетах. Стили react-flow (background, edges, handles, controls, minimap) берут цвета из того же объекта темы. Переключателя тем в UI нет, но добавление новой темы = новый объект темы без правки компонентов |
| D7 | Раскладка слоями | Колонка = уровень навигации (глубина от Главной). Главная — одна, колонка 0; её подсценарии — колонка 1 и т.д. Внутри колонки узлы идут вертикально друг под другом. Количество подсценариев любое. **Ребро не может перепрыгнуть через слой:** при создании связи «через колонку» целевой подсценарий переносится в ближайший следующий слой (в конец, под низ). Связи можно создавать и **переназначать в любой момент** (reconnect на другой источник/цель) — при переназначении действует то же правило: узел перемещается в колонку, непосредственно следующую за колонкой нового источника, чтобы не было пересечений. Внутри слоя пользователь может менять порядок перетаскиванием — порядок персистентен (хранится на сервере) |
| D8 | Типы МИПа | МИП бывает одностраничным и многостраничным. **Одностраничный** = только Форма заявки (степперная форма, пошаговое заполнение) — форма является единственным «слоем» карты. **Многостраничный** = Главная + Подсценарии (+ форма в конце воронки: 99% МИПов завершаются созданием заявки). Главная и Подсценарии относятся только к многостраничным МИПам. **Главная не обязательна:** карта может начинаться без неё (вместо неё может быть, например, Форма заявки) — удаление Главной разрешено, layout-движок обязан работать без неё (глубина считается от корневых узлов графа). **Форм заявки в карте может быть любое количество**, форма может появляться из любого подсценария (решение владельца по Q-7); отдельного поля «тип МИПа» в данных карты нет — состав определяется узлами. Первая кнопка левого сайдбара добавляет узлы (Главная / Подсценарий / Форма заявки), вторая — элементы внутрь выбранного узла |
| D9 | Точки подключения рёбер | Точки входа рёбер — **на краю блока-узла**, а не в произвольной точке: рёбра распределяются вдоль края блока либо сводятся в одну общую точку; пересечения рёбер на подходе допустимы (решение владельца по Q-10). Это снимает проблему сжатых узлов: отображение ребра не зависит от того, виден ли конкретный элемент внутри блока |
| D10 | Панель атрибутов — только элементы | Правая панель атрибутов существует **только для элементов** (решение владельца по Q-12). Если позже появятся настройки у самого блока-страницы или другой сущности — они будут показываться в той же панели на том же месте; механизм рендера (через PropertyRenderer или отдельно) решить по ходу реализации и изучения дизайна |
| D11 | Назначение карты | Карта МИПа (JSON) — **спецификация для разработчика**, а не исполняемый артефакт: по ней разработчик собирает рабочий МИП, сам JSON «вживую» не исполняется. Следствие: редактор не обязан блокировать комбинации, бессмысленные с точки зрения рантайма (например, required-поле, скрытое по умолчанию сложной логикой) — валидация ограничивается структурными инвариантами графа (решение владельца по Q-15) |
| D12 | Форма заявки в слоях | Форма заявки — **не особый случай** layout-движка (решение владельца по Q-11): участвует в слоях на общих основаниях (глубина по входящим связям, если они есть). В многостраничном МИПе может стоять в колонке сразу после Главной; в одностраничном — вместо Главной как единственный узел карты. Правило запрета перескока (D7) распространяется и на связи с формой |
| D13 | Подсценарии — сущности, страницы МИПа | Подсценарии хранятся как **самостоятельные сущности** карты, а не вложенные записи внутри Главной. Главная — первый шаг сценария; каждый подсценарий в рабочем МИПе станет **отдельной страницей**. Узлы-страницы — **верхнеуровневые сущности**: выше них только само приложение (карта). Добавляются последовательно из первой кнопки меню добавления узлов; каждый новый получает следующий **порядковый номер (0, 1, 2, 3, …)** — персистентную позицию, хранимую как часть сущности. Связи между страницами образуются и изменяются в любой момент поверх этих позиций; при привязке/перепривязке узел перемещается в колонку, напрямую следующую за колонкой источника связи (D7). Колонка определяется связями; порядок внутри колонки по умолчанию — порядковый номер, далее пользователь меняет его drag'ом |

## 2. Что видно на макетах (основание для задач)

**Каркас:** TopBar (поиск, «Сохранить», «Предпросмотр», «На согласование») · левый вертикальный тулбар (4 иконки: 1-я — меню добавления узлов «Главная / Подсценарий / Форма заявки», 2-я — меню добавления элементов в выбранный узел, далее JSON и навигация; AI-ассистента нет — удалён по замечанию владельца) · canvas · панель атрибутов справа · нижние контролы (undo/redo, fit, zoom −/%, +, миникарта).

**Пустое состояние (макет «меню-добавления-и-заглушка-пустого-проекта»):** пустой канвас с иллюстрацией-пазлами и текстом «Здесь пока пусто / Добавьте первую колонку, чтобы начать проектировать сервис» (упоминание «стикера» из исходного макета отменено владельцем — сущности нет, Q-6 закрыт).

**Узлы:** «Главная», «Подсценарий» (с подписью уровня навигации), «Форма заявки» (чип «Одностраничная»/«Степперная», подпись «Поля для заполнения пользователем», внутри — шаги горизонтальными колонками, у каждого шага корзина и «+»). У каждого узла — иконка удаления (корзина). Форма заявки может быть единственным узлом карты (одностраничный МИП, D8).

**Элементы внутри узлов:** карточка с иконкой, основным/дополнительным текстом и чипом типа («List item», «Button», «FAQ», «Search user»). Скролла внутри узла **нет** (замечание владельца, отменяет чтение макета «…скроллинг-при-большом-количестве»): при избытке элементов (порог — **более 6 элементов**, решение владельца по Q-14) узел автосжимается и показывает кнопку раскрытия (expand) для просмотра всех элементов.

**Связи:** source-handle на правом краю карточки элемента (не узла целиком) → ребро к узлу подсценария; точка входа — на краю блока-узла, рёбра распределяются вдоль края или сведены в одну точку, пересечения допустимы (D9). При наведении целевой узел подсвечивается.

**Панель атрибутов (справа):** заголовок типа + описание; поля: string с required-маркером и placeholder-примером, multiline, boolean-switch, enum-группа («Тип» кнопки: Текстовая/Вторичная), IconPicker (поиск + сетка + «Смотреть все»), file-вложение (CSV-шаблон FAQ), device-url-map (`{alpha, sigma, mobile}`); секции «Тип», «Настройки»; условная видимость (в FAQ «Вложение*» появляется при включённой «Загрузка файлом»); «Комментарий для разработки» у всех элементов. (Термин: называем «панель атрибутов», не «инспектор» — замечание владельца.)

**Бейджи:** чипы типа, «Одностраничная», «Ссылка 1», платформенные теги (Sigma, Omega, «Есть ссылки»). Платформенные теги сейчас не реализуются — оставить расширяемое место под бейджи в карточке, логика позже (пометка владельца, Q-4).

**Сложная логика (условная видимость):** у элемента-источника (v1 — Select) в панели атрибутов включается режим «Сложная логика» (когда элемент выделен); после включения у каждого option появляется source-handle, из которого протягивается связь к другому элементу формы. Смысл: «при выборе этой опции в первом Select появляется второй Select с другими опциями» (макет «ГОСБ — список Московских банков»). Заказчикам сейчас нужна логика с селектами, но проектируется расширяемо — под будущие Checkbox/Radio и др. Детальный дизайн: `дизайн-сложная-логика.md` (из соседнего чата, лежит в `/mnt/agents/output/`).

**Раскладка:** узлы расположены колонками по уровню навигации — Главная слева, её подсценарии следующей колонкой друг под другом (макет «связь-между-элементами-скроллинг-при-большом-количестве»), их подсценарии — следующей колонкой и т.д. Свободного перетаскивания узлов по канвасу нет.

## 3. Архитектурные принципы (обязательны для реализующего агента)

1. **Никакого хардкода полей панели атрибутов.** Состав полей и редакторов определяется схемой из `IElementSchemaProvider` + метаинформацией проектных схем (D4). Маппинг типа атрибута → компонент редактора — через расширяемый реестр (`PropertyEditorRegistry`), а не switch по именам элементов.
2. **Все визуальные сущности — из Flamingo** (fork MUI v4): Button, Switch, TextField, Chip, IconButton, Popover, Snackbar и т.д.; **все кнопки и иконки — из дизайн-системы, самописных иконок нет** (замечание владельца). Самописная вёрстка/CSS — только там, где Flamingo не покрывает (canvas-специфика react-flow).
3. **Тема как система, по умолчанию одна (D6).** Объект темы (palette + overrides) по механике MUI v4, `ThemeProvider` на корне приложения. Все цвета — только из темы: и Flamingo-компоненты, и стили react-flow (background, dots, handles, edges, controls, minimap). Сейчас тема одна — как на макетах; добавление новой = новый объект темы без правки компонентов.
4. **Адаптер domain ↔ react-flow.** Домен (`ServiceGraph`) не знает о react-flow; react-flow не знает о домене. Мапперы в одну и другую сторону — единственная точка контакта.
5. **Все мутации — через CommandBus** (Immer `produceWithPatches`, execute/undo/redo). Прямые setState-мутации графа запрещены.
6. **Правила слоёв из handoff.md §8.2** соблюдаются (eslint-plugin-boundaries следит): react-flow, Flamingo, Effector — только в presentation/infrastructure, не в domain.
7. **Инварианты в UI.** Результат `validateGraph()` отображается на узлах (подсветка + сообщение), а не только в тестах.

## 4. Задачи

### E0. Предпосылки (блокируют canvas, из handoff Next Steps)

**T-001 CommandBus.** `src/application/commands/`: интерфейс `Command` (execute/undo/redo), класс `CommandBus` на Immer-патчах, команда `AddFormComponent` как референс. Критерий: тесты execute→undo→redo возвращают исходное состояние.

**T-002 DI-контейнер.** `src/infrastructure/container.ts`: Awilix, `InjectionMode.PROXY`, деструктуризация в конструкторах (ADR-04). Cradle: idGenerator, clock, elementSchemaProvider, commandBus. Подключение в `bootstrap.tsx`. Критерий: build/test зелёные, порты резолвятся из контейнера.

**T-003 Фикс typecheck.** Расхождение `FormStepSchema` (без `components`) vs использование `step.components` в инварианте `single-attachment-per-form`. Решение о форме модели — за владельцем; до решения CI блокирован. 6 ошибок `tsc --noEmit`.

**T-004 Доменная модель: страницы и связи.** Подсценарии — **самостоятельные верхнеуровневые сущности** карты (D13): выше них только само приложение; каждый подсценарий = страница будущего МИПа, Главная — первый шаг сценария. Каждая сущность-страница при создании получает следующий **порядковый номер** (`orderIndex`: 0, 1, 2, 3, …) — персистентную позицию, хранимую в самой сущности (это и есть ответ на Q-5: явное поле у подсценария, а не порядок в массиве родителя). В текущей модели (handoff §3) у HomePage/SubScenario просто массивы `listItems[]` — сущности «связь от конкретного элемента к подсценарию» нет, а ребро на канвасе исходит от элемента. Добавить в domain: страницы как коллекцию верхнего уровня в ServiceGraph (не вложенную в Главную), поле `orderIndex`, модель связи (elementId → subScenarioId) с поддержкой переназначения (reconnect), Zod-схемы. Без этой задачи T-030 маппит рёбра из несуществующих данных. Unit-тесты схемы. Зависит от: — (domain-слой).

### E1. Тема редактора (D6)

**T-010 Тема редактора.** `src/presentation/theme/editorTheme.ts`: объект темы по механике MUI v4 — palette (фон canvas, узлы, accent активного switch — зелёный с макетов, primary тёмной кнопки «На согласование», edges/handles/миникарта, чипы) + overrides для Flamingo-компонентов. Провайдер темы на корне редактора. Тема одна; API модуля (getTheme/createTheme) проектируется так, чтобы добавление второй темы не трогало компоненты. Критерий: в компонентах нет литеральных hex — только токены темы.

**T-011 Стилизация react-flow под тему.** Кастомные Controls/MiniMap/Background, цвета — из объекта темы (T-010). Нижняя панель по макету: undo/redo отдельной группой слева, справа fit / zoom-out / % / zoom-in / minimap-toggle. Критерий: контролы визуально соответствуют макету, цвета берутся из темы.

### E2. Каркас страницы редактора

**T-020 TopBar.** Поисковое поле (Flamingo TextField с иконкой), кнопки «Сохранить» (text), «Предпросмотр» (secondary), «На согласование» (primary dark). Действия на этом этапе — заглушки-обработчики, разметка и состояния реальные. Зависит от: T-010.

**T-021 Левый тулбар.** Вертикальная панель из **4** IconButton с active-состоянием (пятая иконка AI-ассистента удалена — замечание владельца). Все кнопки и иконки — из дизайн-системы Flamingo, самописных иконок нет (замечание владельца). Кнопки 1 и 2 — не панели, а меню добавления: кнопка 1 — узлы («Главная / Подсценарий / Форма заявки», макет «меню-добавления-и-заглушка-пустого-проекта»), кнопка 2 — элементы в выбранный узел (макет «пример-подсценариев-с-элементами»). Кнопки 3–4 (JSON / навигация) — переключают панели-заглушки (назначение не подтверждено, Q-1). Зависит от: T-010.

**T-022 EditorPage-компоновка.** Сетка страницы: TopBar сверху, тулбар слева, canvas в центре, панель атрибутов справа (скрыта, пока нет выделения). Компоновка собирается **полностью из компонентов дизайн-системы Flamingo** (Box/Grid/Drawer и т.п.) — самописной вёрстки каркаса нет. Заменяет текущую заглушку `EditorPage.tsx`. Зависит от: T-010, T-011.

**T-024 Пустое состояние канваса.** Экран-заглушка по макету «меню-добавления-и-заглушка-пустого-проекта»: иллюстрация-пазлы, заголовок «Здесь пока пусто», подсказка «Добавьте первую колонку, чтобы начать проектировать сервис» (упоминание «стикера» из макета отменено владельцем, Q-6). Показывается, когда в графе нет ни одного узла; скрывается после добавления первого. Иллюстрация — ассет из макета (экспорт png/svg). Зависит от: T-022.

**T-023 Уведомления (Snackbar).** Сервис уведомлений на Flamingo Snackbar + крюк/фасад для presentation. Триггеры — **только важные действия с файлом**: успешное сохранение, ошибка сохранения/экспорта, критический отказ команды. Undo/redo в snackbar **не** дублируются; штатное удаление узла/элемента уведомления не требует (замечание владельца). Единая точка вызова — не размазывать `<Snackbar>` по компонентам. Критерий: сохранение показывает snackbar; ошибка сохранения — snackbar с сообщением; undo/redo — молча. Зависит от: T-001, T-022.

### E3. Canvas-ядро (react-flow / @xyflow/react)

**T-030 Адаптер graph ↔ flow.** `graphToFlow(graph)`: ServiceGraph → nodes/edges (узлы Home/SubScenario/Form, рёбра из связей listItem→subScenario). Обратный маппинг — только связи и порядок внутри слоёв; координаты не персистентны (D2), позиции вычисляет layout-движок (T-036). Чистые функции, unit-тесты. Зависит от: T-001.

**T-031 Кастомные узлы.** «Кастомный узел» — термин react-flow: содержимое каждой ноды рендерится нашим React-компонентом (а не дефолтным прямоугольником библиотеки) — так рисуются карточки с элементами, чипами и корзиной по макетам. Реестр `nodeTypes`: `ScenarioNode` (заголовок + подпись + корзина + список элементов), `FormNode` (D1: заголовок «Форма заявки» + чип «Одностраничная»/«Степперная» + корзина; шаги — горизонтальные колонки внутри узла, у каждого шага заголовок, корзина и «+»; добавление шага — отдельное действие), строка-элемент `ElementCard` (иконка, основной/доп. текст, чип типа, handle справа). Карточки — Flamingo Card/CardContent. Зависит от: T-011, T-030.

**T-032 Рёбра и связи.** Source-handle на элементе, target — узел подсценария. Точки входа рёбер в целевой узел — по D9: вдоль края блока или сведены в одну общую точку, пересечения допустимы. Создание связи drag'ом, удаление, **переназначение (reconnect) существующей связи на другой источник/цель** (D7/D13: связи можно менять в любой момент), hover-подсветка целевого узла (серый фон + рамка по макету). Связь = команда `ConnectElements`, переназначение = команда `ReconnectElements`. Зависит от: T-031, T-035.

**T-033 Автосжатие узла при избытке элементов.** Скролл внутри узла **не реализуем** (замечание владельца). При превышении порога — **более 6 элементов** (Q-14, решение владельца) — узел автосжимается: список обрезается/уплотняется, появляется кнопка раскрытия (expand), показывающая все элементы. Handles и рёбра обязаны корректно позиционироваться в сжатом и развёрнутом состояниях (вызов `updateNodeInternals` при смене состояния); благодаря D9 входящие рёбра приходят на край блока и не зависят от видимости конкретного элемента. Порог — константа в одном месте. Зависит от: T-031, T-032.

**T-034 Добавление/удаление.** Два меню из левого сайдбара (T-021): узлы — «Главная / Подсценарий / Форма заявки» (Главная доступна только если её ещё нет; форм заявки может быть любое количество — ограничений по типу МИПа в меню нет, D8/Q-7); элементы — из `listSchemas()` провайдера (List item, Список, Вопрос-ответ, Текстовое поле, Дата, Сотрудники, Файл, Информационный блок, Чекбокс и т.д.), добавляются в выбранный узел/шаг (в форме — через «+» конкретного шага). Удаление — корзина в заголовке узла/шага, с каскадом связей. Новый узел-страница добавляется последовательно из первой кнопки меню и занимает следующую позицию по порядку создания (`orderIndex` 0, 1, 2, 3…, D13); связь к нему привязывается позже. Зависит от: T-031, T-035, T-036.

**T-035 Команды canvas.** Набор команд поверх CommandBus: `AddScenario`, `RemoveScenario`, `AddForm`, `RemoveForm`, `AddFormStep`, `RemoveFormStep`, `AddElement`, `RemoveElement`, `UpdateElementProps`, `ConnectElements`, `DisconnectElements`, `ReconnectElements` (переназначение связи на другой источник/цель, D7/D13), `ReorderInLayer` (порядок внутри слоя, персистентный). Каждая с unit-тестами undo/redo. Зависит от: T-001.

**T-036 Слоистый layout-движок (D7, D13).** Чистая функция `computeLayout(graph) → позиции узлов`. Колонка узла определяется связями: глубина = длина кратчайшего пути от корневого узла (BFS по рёбрам). Позиция внутри колонки (Y) — вертикальный стек по **порядковому номеру сущности** (`orderIndex` из D13): новый узел без связей занимает свою позицию 0, 1, 2, 3… по порядку создания; пользователь может менять порядок внутри колонки drag'ом. Главная, если есть, — колонка 0. Главная **необязательна** (D8): карта может начинаться без неё (в т.ч. одностраничный МИП = единственный узел «Форма заявки») — движок обязан работать в этом случае: глубина считается от корневых узлов графа (узлов без входящих рёбер), каждый несвязанный подграф раскладывается от своего корня. Правило запрета перескока: при `ConnectElements` и `ReconnectElements` в слой глубже чем «текущий + 1» целевой подсценарий переносится в ближайший следующий слой за источником (в конец колонки) — это часть команды connect/reconnect, не пост-обработка; при отсоединении связи (DisconnectElements) узел остаётся на своей позиции по `orderIndex`. Форма заявки участвует в слоях на общих основаниях (D12): глубина по входящим связям, если они есть; в многостраничном МИПе может стоять сразу после Главной. Переупорядочивание внутри слоя — вертикальный drag узла (react-flow drag с ограничением по оси X или собственный механизм), результат — команда `ReorderInLayer` (обновляет `orderIndex`). Unit-тесты: глубины, перенос при перескоке, стабильность порядка по orderIndex, одиночная форма. Зависит от: T-030, T-035.

**T-037 Сложная логика (условная видимость элементов).** По дизайн-документу `/mnt/agents/output/дизайн-сложная-логика.md` (из соседнего чата) и макету `/mnt/agents/upload/сложная-логика-госб-список-московских-банков.png`. Суть: у выделенного элемента-источника (v1 — только Select) в панели атрибутов включается «Сложная логика» (чип на карточке + свитч в панели); у каждого option появляется source-handle → ребро к другому элементу формы = правило «option выбран → целевой элемент видим». Цель скрыта по умолчанию, неявное ИЛИ между правилами. Правила — отдельная коллекция `logicRules` в ServiceGraph; условие — discriminated union `LogicCondition` (расширяемо: позже Checkbox/Radio без смены UI-парадигмы). Команды `AddLogicRule`/`RemoveLogicRule` через CommandBus; выключение режима при наличии правил — с подтверждением и каскадным удалением рёбер. Никакого редактора выражений и AND/OR — аудитория бизнес-пользователи. Рёбра сложной логики между элементами одной FormNode (стрелка «Select → Select» внутри блока формы) — штатные рёбра react-flow от handle к handle; ни собственной отрисовки, ни выноса элементов в отдельные ноды не требуется, D1 не меняется (решение владельца по Q-9). Инвариант «required-поле не может быть целью скрытия» **не вводится** (решение владельца по Q-15): карта — спецификация для разработчика, а не исполняемый артефакт (D11), редактор такие комбинации не блокирует. Зависит от: T-031, T-032, T-035, T-041.

### E4. Schema-driven панель атрибутов

**T-040 PropertyEditorRegistry.** Реестр `attributeType → React-компонент редактора`. Встроенные маппинги: `string → TextField`, `multiline → TextareaAutosize`, `boolean → Switch`, `enum → SwitchGroup` (по макету «Тип») или Select. Расширение — регистрацией нового редактора, без правки панели атрибутов. Критерий: добавление фиктивного типа в тесте рендерит зарегистрированный редактор. Зависит от: T-010.

**T-041 PropertyRenderer.** Рендерит панель атрибутов по схеме элемента (`getSchema(kind)`) + метаинформации проектных схем (D4): заголовок типа + описание, секции («Тип», «Настройки»), порядок полей, label/helperText, required-маркеры, placeholder-примеры, условная видимость (кейс FAQ: «Вложение*» при «Загрузка файлом» = true). Поле «Комментарий для разработки» — универсально для всех элементов. Зависит от: T-040.

**T-042 Сложные редакторы.** (а) `IconPicker`: поиск + сетка иконок + «Смотреть все»; (б) `AttachmentField`: кнопка «Выберите файл», CSV-шаблон для FAQ (ссылка «Шаблон для заполнения»); (в) `DeviceUrlMapEditor`: поле ссылки как map `{alpha, sigma, mobile}`. Платформенные теги не реализуются — только расширяемое место под бейджи (пометка владельца, Q-4). Зависит от: T-040.

**T-043 Запись и валидация.** Изменение любого поля → команда `UpdateElementProps` (undo/redo из коробки). После каждой команды — `validateGraph()`, нарушения подсвечиваются на соответствующих узлах canvas (рамка + тултип с message инварианта). Зависит от: T-035, T-041.

## 6. Открытые вопросы (не блокируют старт E0–E1)

- **Q-1. Назначение кнопок 3 и 4 левого тулбара.** На макетах левый вертикальный тулбар содержит 4 иконки. Кнопки 1–2 подтверждены макетами: (1) меню добавления узлов «Главная / Подсценарий / Форма заявки», (2) меню добавления элементов в выбранный узел. Пятая иконка (AI-ассистент) удалена по замечанию владельца. Оформление подтверждено владельцем: **все кнопки и иконки тулбара — из дизайн-системы Flamingo** (самописных иконок нет). Назначение кнопок 3–4 (предположительно JSON-представление и дерево навигации) не подтверждено — реализуются как панели-заглушки до уточнения (T-021).
- **Q-3. Контракт микрофронтенда.** Blueprint-studio встраивается как микрофронтенд (handoff §6). Не определено: (а) что экспонируется наружу (`exposes` — страница редактора целиком или отдельные маршруты); (б) какие зависимости шарятся с хостом (`shared` — React, Flamingo, Effector?); (в) кто владеет роутингом — хост отдаёт редактору базовый путь или редактор регистрирует свои маршруты сам. **Что нужно:** контракт от команды хост-приложения. Влияет на сборку (Rsbuild Module Federation), на canvas-задачи не влияет.
- **Q-4. Платформенные теги (Sigma, Omega, «Есть ссылки») — пометка, не вопрос.** Решение владельца: сейчас не важны — **оставить возможность под них** (расширяемое место в карточке/узле, без логики). Скорее всего это просто настройка ссылки внутри Typography — уточним позже, до реализации T-042 логику не проектировать.
- ~~Q-5~~ → решено владельцем: порядок хранится как **явное поле у самой сущности** (`orderIndex`: 0, 1, 2, 3… по порядку добавления) — см. D13, T-004. Осталось согласовать с бэкенд-контрактом название поля.
- ~~Q-6~~ → закрыт владельцем: сущности «стикер» нет (упоминание — артефакт текста на макете пустого состояния). Стикер не реализуется; текст подсказки в T-024 упрощён до «Добавьте первую колонку, чтобы начать проектировать сервис».
- ~~Q-7~~ → решено владельцем: форм заявки в карте может быть **любое количество**, форма может появляться из любого подсценария. Ограничений в меню добавления узлов по типу МИПа нет (T-034); состав карты произвольный — отдельное поле «тип МИПа» не требуется (см. D8, D12).
- ~~Q-8~~ → решено владельцем: пакет preview-элементов lib-app-core **будет разработан и использован здесь**. T-051 остаётся в плане как задача с этой внешней зависимостью — выполняется после получения пакета.
- ~~Q-9~~ → решено: рёбра «Select → Select» внутри одной FormNode — штатные рёбра react-flow, проблемы нет (зафиксировано в T-037).
- ~~Q-11~~ → решено: D12 — форма участвует в слоях на общих основаниях, может стоять сразу после Главной или вместо неё.

## 8. Общие критерии приёмки эпика

1. По макетам воспроизведены: главный экран, пустое состояние, узлы с элементами (автосжатие + expand вместо скролла), форма заявки с горизонтальными шагами, связи, сложная логика (option → элемент), панели атрибутов: Button / List item / FAQ / Search user / Ссылка.
2. Ни одно поле панели атрибутов не захардкожено под конкретный элемент — состав определяется схемой element-schemas + метаинформацией проектных схем (D4).
3. Undo/redo работает на всех операциях canvas и панели атрибутов.
4. Раскладка слоями работает по D7: колонка = глубина от Главной; связь через слой переносит целевой узел в ближайший следующий слой; порядок внутри слоя меняется drag'ом и персистентен.
5. Все цвета редактора берутся из объекта темы — ни одного литерального hex в компонентах; добавление новой темы не требует правки компонентов (D6).
6. Действия сохранения/удаления/ошибок сопровождаются уведомлениями Snackbar (T-023).
7. `npm run test`, `npm run lint`, `npm run build` — зелёные; правила слоёв не нарушены.
