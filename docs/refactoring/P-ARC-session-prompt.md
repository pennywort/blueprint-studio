## Роль и цель

Ты — архитектор и исполнитель в проекте blueprint-studio (редактор архитектурных карт
`ServiceBlueprint`, AGENTS.md §1). Работаешь в два этапа:

- **Этап A — исследование и решение (только чтение).** Главный вопрос: **почему у элемента
  несколько источников схемы и какой из них должен быть источником правды.** Плюс тот же вопрос
  про переходы между экранами. Результат — разбор и вопросы владельцу. Код не меняешь.
- **Этап B — исправления, не требующие решения владельца:** R-ARC-1 (баг undo) и R-ARC-2
  (проверка инвариантов в `CommandBus`).

Этапы независимы: начни с A (это главное), B делай в той же сессии после того, как отправишь
владельцу вопросы этапа A. Не жди ответа владельца, чтобы приступить к B.

## Этап A. Почему много источников схем элементов

### Что уже известно (проверь, не принимай на веру)

Атрибуты одного вида элемента (`kind`) описаны как минимум в трёх местах:

| #   | Где                                                                                                                              | Что там                                                   | Откуда взялось (гипотеза)                                                                                     |
| --- | -------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 1   | `src/domain/model/form-components.ts`, `canvas-element.ts` (zod)                                                                 | форма данных, которая хранится в `ServiceGraph`; enum'ы   | доменная модель (§4b: источник истины об экране)                                                              |
| 2   | `src/infrastructure/element-schemas/*.json` + `manifest-schema-provider.ts`, порт `application/ports/element-schema-provider.ts` | `key`, `type`, `required`                                 | ADR-07: stub внешнего пакета `element-schemas` (lib-app-core), к которому нет доступа; замена = новый адаптер |
| 3   | `src/presentation/features/attributes/element-attribute-meta.ts`                                                                 | label, placeholder, секции, **опции enum**, `visibleWhen` | D4: «проектные схемы» поверх element-schemas                                                                  |

Ещё знание о видах размазано по: `domain/element-kinds.ts` (`ELEMENT_KIND_RULES`),
`presentation/features/canvas/default-elements.ts` (значения по умолчанию, `switch` по kind),
`presentation/labels/editor-labels.ts` (названия видов), `presentation/features/attributes/attributes-panel.tsx`
(`isValueCompatible` — признаёт несовместимость манифеста и домена: такие поля read-only).

### Что выяснить

1. **Полная карта источников.** Найди ВСЕ места, где описан вид элемента или его атрибут
   (используй субагент `code-finder`; поиск по каждому `kind` и по ключам атрибутов). Для каждого:
   что хранит, кто читает (domain / команды / панель / канвас / сериализация), кто пишет.
2. **История — почему так получилось.** `git log --oneline -S '<символ>' -- <файл>` по
   `element-manifest.json`, `page-element-manifest.json`, `element-attribute-meta.ts`,
   `form-components.ts`, `default-elements.ts`; прочитай сообщения коммитов и комментарии в коде
   с пометками `[owner …]`, ADR, D, T. Ответь: какие источники — **осознанное решение** (ADR-07,
   D4), а какие — **случайное дублирование**.
3. **Матрица расхождений.** Для каждого `kind` × атрибут: есть ли поле в zod, в манифесте, в мете;
   совпадают ли тип, обязательность, набор опций enum. Отдельно — атрибуты, которые есть только
   вне zod (нарушение §4b), и поля zod, которые панель не может редактировать.
4. **Роли, а не файлы.** Разложи знание о виде элемента на роли: (а) форма хранимых данных;
   (б) внешний контракт `element-schemas`; (в) правила редактора (семейство, связи, лимиты);
   (г) значения по умолчанию; (д) представление в панели (подписи, секции, порядок);
   (е) условная видимость. Для каждой роли — где должна жить по конституции §2, D4, ADR-07, §4b,
   и где живёт сейчас.
5. **Сверка с образцом реальной схемы** (`docs/пример-схемы-элемента.json`): какие роли из п. 4
   внешняя схема закрывает сама (тип, enum, default, описание), какие — нет (подписи по-русски,
   секции панели, `visibleWhen`, правила редактора). Отсюда — что из меты и умолчаний должно
   приходить через порт, а что остаётся проектной схемой D4. Хватает ли порта `ElementSchema`
   (`application/ports/element-schema-provider.ts`), чтобы донести enum/default, или его надо
   расширять (расширение порта — вопрос владельцу).
6. **Ограничения, которые НЕЛЬЗЯ нарушать.** Формат реального `element-schemas` неизвестен
   (П2) — не придумывай его. Внешний контракт — только за портом, адаптер нормализует (правило 2).
   Мета атрибутов — проектные схемы (D4) — решение не обсуждается без владельца.

### Переходы между экранами (R-ARC-4) — тот же разбор, короче

«Куда ведёт экран» сейчас выражено тремя способами: `SubScenario.children` (вложенность, канвас
её сплющивает — `domain/graph-walk.ts`), `ServiceGraph.links` (`PageLink`, стрелки канваса),
`Scenario.type='application'` + `applicationFormId`. Выясни по истории и спекам
(`docs/business-requirements.md`, «БТ раздел 7» в комментариях), зачем каждый, кто их пишет и читает,
могут ли они противоречить друг другу. Ответь, что увидит генератор UI (§4b).

## Этап B. Исправления без решения владельца

Делай по `R-ARC-architecture.md`, шаги R-ARC-1, затем R-ARC-2. Перед правкой прочитай только
файлы, названные в шаге.

- **R-ARC-1** — undo-история не должна переживать смену графа (`editor-store.ts`,
  `application/commands/command-bus.ts`). Сначала докажи баг чтением кода: путь «проект A, правка →
  список → проект без сохранённой карты → Undo». Проверка — `npm run ui` по сценарию шага.
  Коммит `fix(editor): R-ARC-1 — …`.
- **R-ARC-2** — `validateGraph` один раз в `CommandBus.execute`, убрать копии из 27 команд.
  **Не меняй** правило «весь граф должен быть валиден» — это вопрос владельцу (в шаге указаны
  варианты); добавь его к вопросам этапа A. Проверь: отказы команд показываются тем же Snackbar
  с тем же текстом. Коммит `refactor(commands): R-ARC-2 — …`.

После шагов отметь ✅ в `R-ARC-architecture.md` (дата, коммит) и статус в `README.md`.

## Правила (кратко; полный текст — AGENTS.md)

- Тесты не пишем и не запускаем. Проверка — `npm run ui`; `verify` + `rules` прогонит pre-commit.
- Код правь инструментами Edit/Write, не shell. Комментарии — по-русски со ссылкой (R-ARC-N, R-SCH-N, ADR, D).
- Не меняй конституцию, D1–D13, ADR — только предлагай владельцу.
- Нашёл ещё один параллельный механизм или дрейф — допиши в план, не латай молча (§4a).
- Не уверен, осознанное ли решение, — считай осознанным и спроси.
- Git: рабочая ветка, отдельные коммиты, затем merge в `master` (AGENTS.md §7). Если локальный
  `master` разошёлся с `origin/master` — не сбрасывай и не force-push'ь, спроси владельца.
