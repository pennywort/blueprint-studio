## R-ARC-1. Сброс undo-истории при смене графа (баг, риск низкий)

**Факт.** `CommandBus` — singleton в DI (`infrastructure/container.ts`, `asClass(CommandBus).singleton()`),
хранит `undoStack`/`redoStack` патчей Immer. Граф живёт в React state страницы
(`presentation/features/canvas/editor-store.ts`, `useEditorStore`). `commandBus.reset()` вызывается
ТОЛЬКО когда `graphRepository.load()` вернул сохранённую карту (`editor-store.ts:44`).

**Чем грозит.** Открыл проект A, сделал правки → вернулся к списку → открыл B, у которого нет
сохранённой карты (демо, «Стенд производительности», новый проект): `load()` → `null`, reset не
вызван. Undo применит inverse-патчи A к графу B — порча графа или исключение Immer.

**Цель.** История принадлежит одному графу: при монтировании редактора / смене `graph.id`
история сбрасывается всегда.

**Направление.** Вызвать `commandBus.reset()` при инициализации `useEditorStore` (до загрузки),
или хранить в истории id графа и отбрасывать чужую. Проверить, что undo/redo внутри одного
проекта не изменились.

**Сценарии `npm run ui`.** A: правка → список → B (демо) → Undo неактивна; внутри A undo/redo работают.

## R-ARC-2. Проверка инвариантов в `CommandBus` (§4a, риск средний)

**Факт.** Блок
`const violations = validateGraph(draft); if (violations.length > 0) throw new InvariantViolationError(violations);`
скопирован в 27 команд `src/application/commands/*.ts` (пример — `add-scenario.ts:23`,
`update-element-props.ts:74`). `command-bus.ts` `execute()` сам инварианты не проверяет.

**Чем грозит.** Новая команда без копии молча обходит инварианты конституции §4 — одно понятие
(«команда не может сделать граф невалидным») держится на дисциплине, а не на механизме.

**Цель.** Проверка — одно место: `CommandBus.execute` после `command.apply(draft)`, внутри
`produceWithPatches`. Из команд блок удаляется.

**[решение владельца] — побочный вопрос.** `validateGraph` проверяет ВЕСЬ граф. Если граф уже
невалиден (загружен старый файл, правило переведено в `error` в `domain/rule-policy.ts`), любая
команда — даже исправляющая — отклоняется. Варианты:

1. Отклонять команду, только если она добавляет НОВЫЕ нарушения (сравнение до/после) — рекомендуется.
2. Оставить как есть (весь граф обязан быть валиден).

**Сценарии `npm run ui`.** Добавление 6-го варианта радио/лимит элементов — отказ со Snackbar, как
раньше; обычные действия проходят.

## R-ARC-3. Один источник атрибутов элемента [решение владельца] (§4b ↓, риск высокий)

**Факт.** Атрибуты одного вида элемента описаны в трёх местах:

| Где                                                          | Что содержит                                                |
| ------------------------------------------------------------ | ----------------------------------------------------------- |
| `domain/model/form-components.ts` (zod)                      | реальные поля и типы, enum'ы (`searchType`, `displayType`)  |
| `infrastructure/element-schemas/*.json` (манифест, ADR-07)   | `key`, `type`, `required` для панели атрибутов              |
| `presentation/features/attributes/element-attribute-meta.ts` | подписи, placeholder, секции, **опции enum**, `visibleWhen` |

Рассогласование уже признано кодом: `attributes-panel.tsx` `isValueCompatible` (~строка 239) —
несовместимые с манифестом значения домена показываются read-only. Опции enum и условная
видимость (`visibleWhen`) — смысл элемента, а живут в presentation (§4b запрещает).

**Чем грозит.** Генератор UI не знает, какой из трёх источников верен; новый атрибут = правка
трёх файлов; расхождения проявляются как «поле не редактируется».

**Вопрос владельцу.**

1. Таблица «kind → атрибуты» (тип, required, опции, visibleWhen) в domain рядом с zod; манифест
   ADR-07 — адаптер, проверяемый против неё; в presentation — только подписи (`editor-labels`). Рекомендуется.
2. Манифест — источник правды, zod генерируется/проверяется из него.
3. Оставить, только перенести опции enum и `visibleWhen` в domain.

Связано: R-CFG-10 (`docs/refactoring/R-CFG-config.md`) — мета атрибутов в JSON.

**Разбор и шаги:** [R-SCH-element-schemas.md](R-SCH-element-schemas.md) §1–6, вопросы В1–В3.

## R-ARC-4. Один механизм перехода между экранами [решение владельца] (§4b ↓, риск высокий)

**Факт.** «С какого экрана куда попадают» выражено тремя способами в `ServiceGraph`:

1. `SubScenario.children` — рекурсивная вложенность (`domain/model/scenario.ts`, ~строка 111).
   Канвас её НЕ показывает: `domain/graph-walk.ts` `walkSubScenarios` сплющивает дерево.
   Используется только `remove-scenario.ts` и `violation-markers.ts`.
2. `ServiceGraph.links` (`PageLink`: элемент → страница) — то, что рисует канвас стрелками.
3. `Scenario.type = 'application'` + `applicationFormId` — ссылка сценария на форму
   (инвариант `domain/invariants/scenario-type-fields.ts`, чистка в `remove-form.ts`).

**Чем грозит.** Генератор навигации не знает, какой источник истинен; из UI можно создать
только (2), (1) и (3) могут противоречить стрелкам.

**Вопрос владельцу.**

1. `links` — единственный переход; `children` и `applicationFormId` удалить с миграцией
   (`infrastructure/persistence/graph-record-migration.ts`) — рекомендуется.
2. Оставить поля, но вычислять их из `links` (производные, не хранимые).
3. Оставить как есть, задокументировать роль каждого.

**Разбор и шаги:** [R-SCH-element-schemas.md](R-SCH-element-schemas.md) §7 — механизмов шесть
(ещё `Scenario.link`/`ListItem.redirectUrl` и `FormComponent.routing`), вопрос В4.

## R-ARC-5. Нарушение несёт id сущности (риск низкий)

**Факт.** `presentation/features/canvas/violation-markers.ts:26` разбирает регуляркой строку
`path` нарушения (`subScenarios[i].children[j]…`), чтобы найти сущность. Формат пути — внутреннее
дело домена (`domain/element-containers.ts` `elementViolationPath`).

**Цель.** `InvariantViolation` (`domain/invariants/index.ts`) получает поле `target: { kind, id }`;
presentation подсвечивает по id, `path` остаётся для сообщений/отладки.

**Сценарии `npm run ui`.** Нарушение лимита элементов и правила логики подсвечиваются на тех же
карточках/блоках, что и раньше.

## R-ARC-6. Доменные правила из presentation — в domain (ADR-20, риск средний)

**Факт.**

- `presentation/features/canvas/layers/layer-policy.ts:39` — `movableKinds` («Главная закреплена
  на уровне 0, переносятся только подсценарии и формы») — правило редактора в UI.
- `presentation/features/canvas/default-elements.ts:47` — `switch` по 12 kind'ам: минимально
  валидный элемент каждого вида — знание схемы, а не UI.

**Цель.** Правило «что переносится между уровнями» — поле в доменной таблице (как
`domain/layer-capacity.ts`), его читают и команда, и `layer-policy`. Значения по умолчанию —
таблица `kind → default` в domain рядом со схемой (вместе с R-ARC-3, если владелец выбрал вариант 1).
В `layer-policy` остаются только размеры/зазоры.

Связано: R-CFG-4 и R-CFG-7 (`docs/refactoring/R-CFG-config.md`) — проверь, не сделано ли там.

## R-ARC-7. Use-case'ы проекта в application (слои, риск средний)

**Факт.** Загрузка, сохранение, экспорт и импорт карты вызывают порты прямо из presentation:
`editor-store.ts` (`graphRepository.load/save`, `graphFileCodec.serialize`),
`pages/project-list/ProjectListPage.tsx:132,148` (`serialize`, `parse`). В `application` нет
сценариев для этих действий.

**Чем грозит.** При переходе на Effector (ADR-06) и в микрофронтенде (ADR-02) логику придётся
выковыривать из React-хуков; правила (сброс истории R-ARC-1, обработка ошибок) дублируются между
страницами.

**Цель.** `application/project/*` — `LoadProject`, `SaveProject`, `ExportProject`, `ImportProject`
(классы под Awilix PROXY, зависимости — порты); presentation вызывает их из контейнера.
