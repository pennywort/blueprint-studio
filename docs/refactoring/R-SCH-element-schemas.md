## 3. Почему так получилось

- Zod (1) и манифест (2) — **две ручные перепечатки одной таблицы** спеки 001 §5.4 (бизнес-требования),
  а не «домен» и «внешний контракт»: формат `element-schemas` тогда был неизвестен (Q3, П2), манифест —
  осознанный stub (ADR-07), но его состав и `required` выдуманы, а не взяты из пакета.
- Мета (3) — осознанное решение D4 («проектные схемы поверх element-schemas»); случайно другое: опции
  enum повторяют zod, а `visibleWhen` (смысл элемента) попал в presentation.
- Умолчания (5), заголовок карточки (7), `isValueCompatible` (8) — случайные дубли: каждая фича Epic 002
  дописала своё знание о виде рядом с собой.
- Реальная схема богаче stub'а: несёт enum, `default`/`x-defaults`, описания, `oneOf`, события
  (`x-events`); имена видов и полей другие (`text-field`, `helperText` vs `caption`, нет `maxLength`).

Порт `ElementSchema` (`key/type/required`) **не донесёт** enum, default, описание, `oneOf`, события,
соответствие `elementType ↔ kind`. Расширять порт — вопрос владельцу (В1, В2), формат — только по
настоящему пакету (П2).

## 5. Целевая модель

```text
domain/model/*.ts (zod)                 ← форма данных, enum-значения          (а)
domain/element-kinds.ts                 ← правила, + primaryTextKey             (в)
domain/element-attributes.ts  (новый)   ← kind → [{ key, editor, visibleWhen? }] (е), порядок
domain/element-defaults.ts    (новый)   ← kind → default, проверка zod          (г)
presentation/.../element-attribute-meta ← только подписи, секции, placeholder   (д)
application/ports/element-schema-provider ← внешний контракт; адаптер сверяет (б) с (а)
```

- Одну таблицу `kind → описание` читают: инварианты и команды (zod), панель (attributes + мета),
  фабрика умолчаний, генератор UI — образец `domain/layer-capacity.ts`, `domain/element-kinds.ts`.
- Расхождения ловятся при старте (как `ManifestSchemaProvider.parse`): каждый ключ атрибутов/меты/
  манифеста — поле zod вида; каждое умолчание проходит `CanvasElementSchema`; enum-опции меты ⊆ zod.
  Расхождение — ошибка в dev-сборке (список «вид.ключ»), а не read-only поле.
- Когда появится `element-schemas`: новый адаптер нормализует `elementType → kind`, `x-defaults` →
  умолчания, `enum` → значения; домен остаётся источником правды о карте, адаптер лишь сообщает о
  расхождениях (новое поле пакета без поля в zod = задача добавить поле, §4b).

## 6. Шаги — элементы

Каждый шаг — один коммит, поведение пользователя не меняется, если не сказано иное.

### R-SCH-1. Проверка согласованности при старте (без решения владельца)

- `domain/element-schema-check.ts` (или в адаптере): ключи манифеста и меты ∈ `hasElementField`,
  enum-опции меты ⊆ `z.enum().options`. В dev — `console.error` со списком; сборка не падает до
  исправления известных расхождений (`datePeriod.noPast/noFuture`) — они в allow-list с ссылкой на R-SCH-5.
- Файлы: новый модуль, `infrastructure/container.ts` (вызов при сборке контейнера).
- **Проверка `npm run ui`:** редактор открывается, панель любого вида — как раньше.

### R-SCH-2. Значения enum — из zod (без решения владельца)

- Мета хранит только подписи `{ value → label }`; список значений панель берёт из zod
  (`domain` хелпер `attributeEnumValues(kind, key)`). Порядок — порядок `z.enum`.
- Файлы: `element-attribute-meta.ts`, `attributes-panel.tsx`, новый хелпер в `domain/model/canvas-element.ts`.
- **Проверка:** Select → «Тип отображения» 3 варианта; Button → тип и расположение; Search user → тип поиска.

### R-SCH-3. Таблица атрибутов в domain [решение владельца В1]

- `domain/element-attributes.ts`: `kind → [{ key, editor, visibleWhen? }]` (тип `ElementAttributeType`
  переезжает из порта в domain). Панель читает её; манифест — только адаптер, сверяемый с ней (R-SCH-1).
  `visibleWhen` переезжает из меты.
- Файлы: новый модуль, `attributes-panel.tsx`, `element-attribute-meta.ts`, `element-schema-provider.ts`,
  `editor-toolbar.tsx` (порядок меню — из R-CFG-7, если сделан).
- **Проверка:** панель каждого вида — тот же состав, порядок, секции; «С поиском» только при dropdown.

### R-SCH-4. Умолчания в domain (= R-ARC-6, часть 2; R-CFG-10 — потом JSON)

- `domain/element-defaults.ts`: `kind → default` (без id), фабрика в presentation — тонкая обёртка;
  при старте каждое умолчание проходит `CanvasElementSchema`.
- **Проверка:** новый элемент каждого вида из тулбара и «+» шага — те же значения, что раньше.

### R-SCH-5. Недоступные поля модели [решение владельца В3] — меняет поведение

- `datePeriod.restrictions` — редактор вложенного объекта или путь ключа `restrictions.noPast`;
  `addressPicker.displayParts` — мультивыбор из enum; заголовок карточки `infoBlock` — `text`
  (`primaryTextKey` в `element-kinds.ts`).
- **Проверка:** чекбоксы ограничений дат сохраняются и переживают undo; карточка Info block показывает текст.

### R-SCH-6. Адаптер настоящего `element-schemas` (после доступа к пакету, П2)

- Расширение порта (enum, default, описание, `elementType ↔ kind`) — по решению В2; таблица
  соответствия имён полей (`caption ↔ helperText`, `maxLength ↔ counter`?) — вопрос команде lib-app-core.

## 7. Переходы между экранами (R-ARC-4)

### Карта механизмов

| #   | Механизм                                                        | Откуда (спека)                          | Кто пишет                                 | Кто читает                                                        |
| --- | --------------------------------------------------------------- | --------------------------------------- | ----------------------------------------- | ----------------------------------------------------------------- |

| T3  | `SubScenario.children` (вложенность)                            | спека 001 §5.3, БТ §7 «навигационный»   | никто (только импорт файла)               | `graph-walk` (сплющивает), `remove-scenario`, `violation-markers` |
| T4  | `Scenario.type` + `applicationFormId`                           | спека 001 §5.3, БТ §7 «сценарий-заявка» | UI всегда `type:'navigation'`; id — никто | инвариант `scenario-type-fields`, чистка в `remove-form`          |
| T5  | `Scenario.link` (type=link) и `ListItem.isRedirect/redirectUrl` | БТ §7 «сценарий-ссылка»                 | никто                                     | инвариант `scenario-type-fields`                                  |
| T6  | `FormComponent.routing { targetStepId, targetScenarioId }`      | спека 001 §5.4, БТ 4.1                  | никто                                     | инвариант §4 #3–5 (`routing-excludes-dynamic-content`)            |

**Почему так.** Спека 001 описала навигацию деревом сценариев (T3–T6, БТ §7: тип — свойство list-item'а:
заявка / ссылка / контейнер). Epic 002 (канвас, D12/D13) ввёл рёбра T1/T2 и стал единственным способом
задать переход из UI, а поля спеки 001 остались в схеме без писателей.

**Противоречия.** T3 «S2 вложен в S1» при стрелке Главная → S2; T4 `type:'navigation'` у подсценария,
в который ведёт стрелка на форму; T6 `targetStepId` ≠ `stepTransitions` того же элемента; T5 ссылка у
сценария и у list-item'а одновременно. Ни один инвариант их не сверяет.

**Что увидит генератор (§4b).** Надёжно — только T1 и T2 (их видит и правит пользователь). Тип перехода
по БТ §7 выводится из цели T1: подсценарий → «навигационный», форма → «заявка»; внешняя ссылка —
поле элемента (T5, сейчас без UI). T3/T4/T6 генератор должен игнорировать или получить их непротиворечивыми.

### Шаги — переходы

- **R-SCH-7 [решение В4].** Схема v4 + миграция в `graph-record-migration.ts`: `children` сплющиваются в
  `subScenarios` (канвас и так их сплющивает), `applicationFormId`, `Scenario.type`, `Scenario.link`,
  `routing` удаляются; `violation-markers`, `remove-scenario`, `remove-form`, `scenario-type-fields`
  упрощаются. **Проверка:** импорт файла v3 с `children` — те же узлы на канвасе; связи не потеряны.
- **R-SCH-8 [решение В4].** Инвариант §4 #3–5 читает переходы (T1/T2 из элемента) вместо `routing` —
  правка конституции §4 только с владельцем. **Проверка:** элемент с переходом и «динамическим
  контентом» даёт нарушение (когда появится UI флага).
- **R-SCH-9.** `domain/transition-kind.ts`: `kind` перехода list-item'а (навигация / заявка / ссылка)
  выводится из цели — функция для генератора и подсказок UI. Внешняя ссылка list-item'а — после В3.
- **Наблюдение (§4a):** T1 и T2 — одно понятие «переход» в двух коллекциях; объединение в union
  `Transition` по `scope` (страница / шаг) — кандидат, только по решению владельца.

## Решения владельца

**2026-10-19.**

- **В1 — один источник, слоями.** Пакет фреймворка даёт схемы всех элементов со всеми атрибутами
  (база). Проект накладывает свой слой: выбирает, какие атрибуты показать в панели, сужает или
  расширяет их состав и добавляет собственные элементы, которых нет в пакете (например,
  комментарий-элемент). Панель рисует поле по типу атрибута; набор типов — конечный.
  Формат схемы и слоя уточняется отдельным проектом — `P-SCH-schema-clarification.md`.
  Шаги R-SCH-3…6 перепланировать после него.
- **В3** — схемы будут на все элементы, слой проекта на каждый из них разрешает/запрещает/расширяет.
  Отдельного «открыть поля сейчас» не нужно — придёт со слоем (R-SCH-5 отменяется).
- **Ошибки (к В5)** — единый реестр правил, строго описанный и в конфиге, а не `if` по проекту
  (configs first) → шаг R-CFG-11.
- **Лимит шагов формы** — отключён в `domain/layer-capacity.ts` (`FORM_STEP_LAYER_CAPACITY = {}`),
  включить обратно — `{ 0: 1 }` (коммит `8ebcd2a`). Демо-карта снова редактируется.
- **В4, В5** — ждут ответа (В4 переформулирован простыми словами в ответе владельцу 2026-10-19).
