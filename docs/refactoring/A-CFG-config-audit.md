## Роль и цель

Ты — архитектор blueprint-studio. Найди в коде правила, ограничения и визуальные решения,
которые сейчас **захардкожены** (ветвления `if kind === …`, константы в компонентах,
дубли одной логики), и предложи, как превратить их в **данные редактируемой конфигурации
редактора**. Цель владельца — гибкость: новое требование заказчика или его отмена =
правка конфига, а не кода.

## Принципы, по которым оцениваешь (AGENTS.md §4a)

1. **Policy as data / table-driven design** — правило живёт в таблице/конфиге; код —
   общий интерпретатор таблицы. Эталон в проекте: `src/domain/layer-capacity.ts`
   (ёмкость уровней: одна таблица читается и инвариантом домена, и подсказками dnd).
2. **Reversible decisions** — любое решение заказчика можно отменить или обратить
   правкой одного значения, без каскада правок по коду.
3. **Open/Closed + Strategy** — новый вид сущности/связи/подсветки добавляется записью
   в конфиг или новой стратегией, ядро не правится.
4. **Одно понятие — один механизм** — сначала объединить дубли общим ядром, потом
   выносить параметры ядра в конфиг. Конфиг поверх двух копий логики — не решение.
5. **Одно правило — один источник** — домен (инварианты, команды) и UI (подсветка, dnd,
   меню, панель атрибутов) читают одно и то же значение.

## Где искать (области — минимум; ищи и сверх списка)

| Область              | Что искать                                                                              |
| -------------------- | --------------------------------------------------------------------------------------- |
| Связи                | какие виды сущностей с какими соединяются, смежность уровней, каскады при переносе      |
| Уровни/слои          | политики слоёв, ёмкость, что переносится между уровнями, закреплённые узлы              |
| Сущности             | `kind`-ветвления: страница/подсценарий/форма/шаг/элемент/вариант; что вкладывается куда |
| Ограничения домена   | инварианты (`src/domain/invariants/*`): лимиты (radio ≤ 5, одно вложение…) как числа    |
| Визуальные состояния | обводки, подсветки, приоритеты (цель связи > dnd > выделение > ошибка), их геометрия    |
| Раскладка            | зазоры, ширины, отступы (`canvas-layout.ts`), стили рёбер (радиус, тип пути)            |
| Меню и действия      | какие действия доступны какой сущности (добавить, удалить, «Сложная логика», dnd)       |
| Тексты               | подписи, сообщения нарушений, «Шаг N», названия видов — кандидаты в словарь             |

## Метод

1. `git status -sb`; правила чтения — AGENTS.md §6 (поиск → диапазон; PROJECT_STATE —
   только `npm run state:summary`). Шумный поиск отдавай субагентам `code-finder`/`Explore`.
2. Для каждой находки зафиксируй: **где** (файл:строка), **что захардкожено**, **сколько
   копий** (параллельные механизмы), **как часто меняется по опыту проекта** (ищи `[owner …]`
   в комментариях и решения в `docs/` — частые правки = первый кандидат).
3. Классифицируй, куда выносить:
   - **A. Доменная таблица (TS-константа в `domain`)** — правило, которое проверяет
     инвариант; меняется разработчиком, но в одном месте.
   - **B. Конфиг редактора (JSON + zod-схема, загрузка через порт `application/ports`)** —
     то, что может настраивать владелец/заказчик без разработчика.
   - **C. Тема/токены (`editor-theme.ts`)** — цвета, толщины, радиусы, отступы.
   - **D. Оставить в коде** — если вынос усложнит больше, чем даст; объясни почему.
4. Предложи **форму конфигурации**: структура (например, `entities`, `connections`,
   `layers`, `visualStates`, `limits`, `labels`), zod-схема, значения по умолчанию,
   где лежит файл, как валидируется при загрузке и что будет при ошибке в конфиге.
   Учитывай: 4 слоя (enforced lint), Module Federation в будущем (никаких `window`),
   immer + CommandBus (конфиг не мутирует граф — только параметризует правила).
5. Оцени каждое предложение: **польза** (гибкость, удаление дублей), **стоимость**
   (файлы, риск), **обратимость** (что надо поменять, чтобы вернуть как было).

## Ограничения

- Код, конфиги и PROJECT_STATE **не меняешь** — только пишешь план.
- Решения D1–D13, ADR и конституцию не пересматриваешь; если вынос их задевает —
  пометь «нужно решение владельца».
- Тесты не пишем и не запускаем (AGENTS.md §4).
- Нет ответа в источниках — не выдумывай, вынеси в «Вопросы владельцу».

## Результат: `docs/refactoring/R-CFG-config.md`

Формат — как у `R-ENT-entities.md` (самодостаточный план для чистой сессии):

1. **Сводка** (до 10 строк): главные кандидаты и ожидаемый эффект.
2. **Карта находок** — таблица: `ID | область | где | что захардкожено | копий | класс A/B/C/D | польза/стоимость`.
3. **Целевая модель конфигурации** — структура, zod-схема (эскиз), загрузка через порт,
   поведение при невалидном конфиге.
4. **Шаги `R-CFG-1…N`** — по порядку: сначала объединение дублей, потом вынос в таблицы
   домена, потом внешний конфиг. Каждый шаг: файлы, что меняется, сценарии `npm run ui`
   для проверки, как откатить. Один шаг = один коммит.
5. **Вопросы владельцу** — до 5, с рекомендуемым вариантом.

Затем добавь строку плана в таблицу `docs/refactoring/README.md` (статус ⏳ ожидает),
закоммить (`docs: план R-CFG — вынос правил редактора в конфигурацию`), push и merge (AGENTS.md §7).
Ответ владельцу — по лимитам AGENTS.md §0: 3–5 главных находок и путь к плану.
