## 4. Как создать change

Папка `openspec/changes/<id>/` (id — из карточки). Используй свои команды OpenSpec для заготовки; содержимое:

| Файл                         | Из чего собирать                                                                                                                                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `proposal.md`                | Why = «Цель»; What Changes = «Состав» по смыслу; Non-goals = «Не входит»; Impact = затронутые capability и слои                                                                                                    |
| `design.md`                  | Полный текст ADR/D-решений из карточки (точечно из `PROJECT_STATE.md` §3 и документов), альтернативы, диаграмма mermaid при пользе; Open Questions — только из `PROJECT_STATE.md` §6 и только относящиеся к change |
| `tasks.md`                   | «Состав» → чек-лист `- [x]` (всё уже реализовано), мелочи — подпунктами. Номера T-xxx — в заголовках пунктов                                                                                                       |
| `specs/<capability>/spec.md` | `## ADDED Requirements` → `### Requirement: …` с `SHALL`; у каждого минимум один `#### Scenario: …` (WHEN/THEN) из «Критериев»                                                                                     |

Capability: `bootstrap-tooling`, `ui-kit-shims`, `service-graph-model`, `invariants`, `element-schemas`, `command-bus`,
`editor-theme`, `editor-shell`, `canvas-layout`, `canvas-nodes`, `canvas-links`, `canvas-selection`, `canvas-dnd`,
`form-steps`, `complex-logic`, `attributes-panel`, `violations`, `search`, `persistence`, `canvas-performance`,
`comment-elements`, `dev-tooling`. Если capability уже есть от прежнего change — пиши `## ADDED`/`## MODIFIED` честно по смыслу.

Проверка: `openspec validate <id> --strict` (если команда есть) — должно пройти.
Размер: proposal ≤ 1 страницы; требований 4–10 на change; не переписывай код словами.

## 5. Коммиты и PR

- Ветка: `openspec/changes` от `main` (создаёт владелец или ты один раз).
- Один change = один коммит; в него входит только `openspec/changes/<id>/`.
- Сообщение (conventional, по-русски; номера задач — из таблицы в карточке и `.replay/COMMIT-REFS.md`):

```
docs(openspec): change <id> — <суть в 5–8 словах> (PR-NN)

Задачи: <T-xxx, …>; решения: <ADR-xx, D-x, …>
```

- Коммитит агент только если владелец разрешил в `PROGRESS.md` (поле «Коммитит агент: да/нет»). Иначе после change владелец коммитит сам.
- После PR-28 (или по решению владельца): `openspec archive <id> --yes` для всех — одним коммитом `chore(openspec): архив changes`.
- Push и PR делает владелец. Никаких `--force`.
