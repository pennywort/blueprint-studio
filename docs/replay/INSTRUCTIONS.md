# INSTRUCTIONS — строгий протокол агента: воспроизведение истории по PR (SDD + OpenSpec)

> Читай ЭТОТ файл целиком в начале КАЖДОЙ сессии. Отступать нельзя. Не уверен — остановись и спроси владельца.
> Окно контекста маленькое: читай только то, что перечислено для текущего шага. Никаких «заодно».

## 0. Роль и цель

Ты строишь историю нового репозитория: 28 PR, каждый = ровно ОДИН OpenSpec change + код среза.
Эталон конечного состояния — тег `final` в репозитории-источнике (remote `source`).
Источник «что делать» — карточка текущего PR: `.replay/cards/PR-NN-*.md`. Журнал — `.replay/PROGRESS.md`.

## 1. Что такое change, а что нет

**Change = ровно одна карточка** (28 штук). Новый change НЕ создаётся для: правки ширины/угла стрелки, цвета, отступа,
fix/revert/refactor-доводки, переименования, опечатки, мелких UI-поправок, «замечаний приёмки».
Такие вещи — **пункты `tasks.md` внутри change** той карточки, к которой относятся (таблица «Мелочи» — в карточке или
`docs/план-pr-openspec.md` §6). Если соблазн создать 29-й change — **стоп, спроси владельца**.

## 2. Пред-условия (делает владелец или ты один раз в самом начале, потом отметь в PROGRESS)

1. Новый пустой репозиторий; в нём `git remote add source <url-старого-репо>` и `git fetch source --tags --no-tags`
   плюс ветки/теги `final` и `legacy/pre-graft` (`git fetch source final legacy/pre-graft` либо локальный путь).
2. Base-коммит в `main`: `.gitignore` (включая `.replay/` и `node_modules`), README, `openspec init`
   (конституция → `openspec/project.md`). Папка `.replay/` (этот файл, карточки, PROGRESS) лежит **вне git**.
3. Проверка: `git rev-parse final legacy/pre-graft` отдаёт два хеша. Нет — СТОП, сообщи владельцу.

## 3. Сессии: как работать с маленьким контекстом

Одна сессия = ОДИН шаг. Шаги: **CODE(NN)**, **DOCS+CLOSE(NN)**. Для размера S — один шаг CODE+DOCS+CLOSE.

Начало сессии (всегда одинаково):

1. Прочитай этот файл.
2. Открой `.replay/PROGRESS.md`, найди «Текущий шаг». Работай только над ним.
3. Прочитай карточку `.replay/cards/PR-NN-*.md`. Больше документов не читай, пока шаг не требует.

Конец сессии (всегда):

1. Обнови строку PR и «Текущий шаг» в `PROGRESS.md`, допиши строку в журнал сессий.
2. Напиши владельцу ровно это (подставь значения):
   `Шаг PR-NN/<ШАГ> завершён. Статус: <статус>. Очисти контекст (/clear) и отправь: «Продолжи по .replay/INSTRUCTIONS.md».`
3. Больше ничего не делай. Не начинай следующий шаг в том же контексте.

Если контекст почти заполнен (>70%) посреди шага — **остановись**, запиши в PROGRESS «Заметки» (что сделано, что осталось,
какая команда падала), попроси владельца очистить контекст. Не дожимай шаг «на остатках».

## 4. Запрещено (нарушение = откат шага)

- Менять `tsconfig`/`eslint` ради зелёной сборки; `@ts-ignore`, `@ts-expect-error`, `eslint-disable`, `any` ради прохода.
- Удалять/комментировать чужие файлы, чтобы собралось. Удалять `.replay/`.
- Писать или запускать тесты; брать из эталона `*.test.*`, `*.fixture.*`, `*.disabled`, `vitest.*`.
- Читать: `node_modules/`, `dist/`, `package-lock.json`, `docs/archive/`, `KIMI.md`, `.kimi/`, целиком `PROJECT_STATE.md` (72 КБ).
  ADR смотреть так: `npm run state:section -- 3` или в старом репо `grep -n "ADR-14" PROJECT_STATE.md`.
- `git push --force`, `git reset --hard` на общих ветках, пуш в `main`, merge без владельца.
- Работать над двумя PR одновременно. Менять порядок PR. Объединять/дробить карточки.
- Выдумывать код/решения. Нет ответа в карточке и источниках — спроси владельца.
- Включать в PR что-то из «Не входит» карточки или файлы, нужные только более поздним PR.

## 5. CODE(NN) — получение кода PR

Ветка: `git switch main && git switch -c change/<id>`. `main` должен содержать все предыдущие PR (статус `merged`);
если предыдущий PR не `merged` — СТОП (стек: PR k+1 ветвится от ветки PR k только по явному разрешению владельца).

**Ключевое правило против конфликтов:** файл берётся из источника **целиком**, а не сливается.
Более поздний PR перезаписывает файл раннего полной версией из `final` — merge-конфликтов не бывает по построению.

### Режим LEGACY (карточка говорит `LEGACY`; PR 01, 02, 05, 06, 07, 08)

1. Список файлов — из карточки («Ключевые пути») и коммитов `legacy/pre-graft`.
2. `git checkout <хеш> -- <пути>` для каждого указанного коммита (хеши — в карточке). Только пути этого PR.
3. Удали из индекса тесты/фикстуры/документацию-хэндофф: `git rm -r --cached` для `*.test.*`, `*.fixture.*`; в `docs/` ничего не бери.
4. Если файл из legacy-коммита противоречит карточке (старая модель до ADR-17) — не правь вручную, СТОП и спроси.

### Режим SLICE (остальные PR)

1. Список файлов: «Ключевые пути» карточки. Если путей нет/мало — найди через `git diff --stat <предыдущий merge> final -- src | head`
   и `git log final --oneline -- <путь>`, но включай только файлы темы этого PR.
2. `git checkout final -- <пути>` (файл целиком).
3. **Вперёд-ссылки.** Запусти `npm run lint`. Каждая ошибка «модуль/символ не найден» — ссылка на более позднюю фичу. Исправляй
   ТОЛЬКО так: (а) удалить использование (опциональный пункт меню, ветку switch, поле контекста); (б) поставить минимальную
   заглушку с комментарием `// СТАБ PR-<k>: <что вернёт PR-k> (ссылка на карточку)`. Список стабов запиши в «Заметки» PROGRESS
   — следующие PR обязаны их убрать.
4. Зависимости (`package.json`): добавляй только пакеты, импортируемые этим PR; версии — как в `final`, `npm i -E <pkg>@<ver>`.

### Гейт качества (оба режима, обязателен перед коммитом)

```
npm run lint        # eslint + tsc --noEmit
npm run build       # rsbuild
grep -rn "@material-ui" src          # должно быть пусто (кроме vendor)
grep -rniE "#[0-9a-f]{3,6}\b" src/presentation --include=*.tsx   # hex в компонентах запрещён (тема — исключение)
```

Не зелёно → исправь (макс. 2 попытки одного рода). Всё ещё красно → статус `BLOCKED`, причина и последние 15 строк ошибки в
«Заметки», остановись и сообщи владельцу. Не «чини» ослаблением правил (§4).

Затем: `git add -A` (только пути PR + package.json + lockfile), коммит conventional по-русски, 1 PR = 1–несколько коммитов
(если PR имеет несколько логических частей — коммит на часть), статус → `code-done`.

## 6. DOCS+CLOSE(NN) — OpenSpec и закрытие

В ветке `change/<id>` создай `openspec/changes/<id>/` (используй свои команды OpenSpec; результат должен содержать):

| Файл                         | Из чего собирать                                                                                                                                                                                                                                    |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `proposal.md`                | «Цель» + «Не входит» карточки; блок Why / What Changes / Impact                                                                                                                                                                                     |
| `design.md`                  | ADR/D-решения из карточки: **полный текст** взять из старого репо (`PROJECT_STATE.md` §3 — только нужные строки), альтернативы, диаграмма слоёв/потока в mermaid при необходимости; «Open Questions» — из §6 PROJECT_STATE, только относящиеся к PR |
| `tasks.md`                   | «Состав» карточки → чек-лист `- [x]` (всё реализовано в CODE) + подпункты-«мелочи»                                                                                                                                                                  |
| `specs/<capability>/spec.md` | `## ADDED Requirements` / `### Requirement:` с `SHALL`, у каждого минимум один `#### Scenario:` (WHEN/THEN) из «Критериев»                                                                                                                          |

Capability (имя папки) — из списка плана §2: `service-graph-model`, `invariants`, `element-schemas`, `command-bus`, `editor-shell`,
`editor-theme`, `canvas-layout`, `canvas-nodes`, `canvas-links`, `canvas-selection`, `canvas-dnd`, `form-steps`, `complex-logic`,
`attributes-panel`, `violations`, `search`, `persistence`, `canvas-performance`, `comment-elements`. Новое имя — только по согласованию.

Проверка: `openspec validate <id> --strict` (если команда есть) — должно пройти. Требования в spec.md описывают то, что **реализовано
в этом PR**, а не будущее.

Закрытие:

1. Коммит `docs(openspec): change <id>` в той же ветке; `git push -u origin change/<id>`.
2. PR: `gh pr create` если доступен, иначе сообщи владельцу название ветки и заголовок. Заголовок = `<тип>: <краткая суть по-русски> (PR-NN)`,
   в теле — цель, список «Состав», ссылка на `openspec/changes/<id>/`.
3. Статус `pr-open`. **Merge делает владелец.** После его сообщения «слито»: `git switch main && git pull`,
   `openspec archive <id> --yes` (если команда есть), коммит `chore(openspec): архив <id>`, статус `merged`, следующий PR.
